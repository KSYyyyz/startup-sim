# Startup Sim 独立游戏化产品文档

Status: product direction baseline
Owner: Codex
Date: 2026-05-18
Vercel frontend: https://startup-sim-khaki.vercel.app

## 1. 产品定位

Startup Sim 的后续目标不再是把 CLI 逐项搬到网页，而是做成一款 AI 原生创业经营模拟独立游戏。

一句话定位：

> 一款以 AI SaaS 创业公司为主题的独立经营模拟游戏。玩家经营办公室、团队、产品、客户、融资和竞争格局，并可以用自然语言向公司下达经营命令，由确定性商业规则和 AI 角色共同生成反馈、冲突和复盘故事。

产品目标：

- 像经营游戏一样可点击、可操作、可观察，而不是只读状态面板。
- 像真实创业一样有现金流、产品、客户、竞品、融资、组织和声誉压力。
- 像 AI 原生游戏一样允许玩家自由输入经营命令，并让董事会、客户、员工、投资人、竞品和媒体以角色化方式回应。
- 为未来可分发独立游戏保留技术空间：Web 先行，后续可包装为桌面版、Steam 版或离线试玩版。

核心原则保持不变：

> 真实商业作为底层逻辑，游戏性作为表层体验。

玩家看到的是办公室、行动、角色、事件、反馈和复盘；PMF、估值、现金流、融资成功率、客户留存和竞争压力由后台计算。

## 2. 调研摘要

### 2.1 经营模拟参考

`Mad Games Tycoon 2` 的启发是“从小公司成长为大公司”的可操作链条。其 Steam 页面强调从车库公司成长为大型公司，建设办公室、生产设施、服务器房，开发不同类型产品，积累 IP，研发或授权引擎，最终扩张到更大的产业位置。对 Startup Sim 的启发不是照搬游戏开发题材，而是建立“公司空间 + 产品管线 + 产业扩张”的中长期成长感。

`Software Inc.` 的价值在于把建筑、市场模拟和软件公司日常运营连接起来。其 Steam 页面强调复杂建筑机制、深度市场模拟、软件公司的日常生活，以及服务器、源代码管理、在线商店等产品运营设施。对 Startup Sim 的启发是：办公室不只是背景图，而应成为系统入口，房间和设施代表真实经营能力。

`Game Dev Tycoon` 的启发是轻量化选择与结果反馈。官方商店描述强调开发过程中的决策会影响结果、研究技术、招聘和管理团队、成为市场领导者。对 Startup Sim 的启发是：复杂的经营推演可以被包装为“选择一个产品方向、投入资源、等待市场反馈”的轻量循环。

`Two Point Hospital` 的启发是房间、员工和运营压力的可视化。它把设施建设、员工管理和运营效率包装成幽默、可读、可观察的经营体验。Startup Sim 不需要做医院式精细寻路，但需要借鉴“房间就是玩法入口、员工状态就是运营反馈”的表现方式。

### 2.2 AI 原生玩法参考

`历史模拟器：崇祯` 的关键启发是 AI 原生策略游戏形态。其 Steam 页面描述为依托 AI 大模型、玩家自由下达诏书来挽救明末危局。对 Startup Sim 的启发是：自由输入不应只是隐藏的文本框，而应成为核心卖点。玩家可以像 CEO 下达经营指令一样表达意图，系统再把它翻译成可计算动作和角色反馈。

`Generative Agents: Interactive Simulacra of Human Behavior` 提供了 AI 角色设计参考：角色需要记录经历、形成反思、检索记忆并规划行为。Startup Sim 不需要一开始做完整多智能体小镇，但可以从轻量角色记忆开始：CFO 记住玩家是否过度烧钱，CTO 记住玩家是否长期忽视产品，投资人记住之前的融资谈判。

`PANGeA` 类研究提供了另一个边界：LLM 可以帮助生成叙事和互动，但必须受到设计规则和验证系统约束。Startup Sim 的 AI 不能随意改写游戏状态；AI 负责解释、叙事、角色化建议和自由命令理解，最终数值变化必须经过确定性规则层。

### 2.3 技术路线参考

Web 仍是第一阶段最合适的平台。Vite/Vercel 支持前端静态部署和 Git 推送自动发布，适合快速迭代和线上试玩。现有前端已经在 Vercel 上可运行，可以继续作为公开试玩入口。

执行顺序采用桌面端优先。Startup Sim 的核心体验是办公室经营、信息面板、行动卡和月度反馈并行呈现，桌面端更适合验证这种经营游戏的主要信息密度。移动端在桌面玩法稳定前只做基础可访问与不崩溃保障，不作为玩法深度和布局打磨的主验收目标。

渲染层建议优先引入 PixiJS。PixiJS 是面向 2D WebGL/WebGPU/Canvas 的高性能渲染系统，适合办公室场景、人物、房间、气泡、事件动画和轻量互动。React 继续负责 HUD、面板、复盘、表单和信息架构，PixiJS 负责游戏画布。

Phaser 可以作为第二阶段备选。Phaser 是更完整的 HTML5 游戏框架，适合状态机、场景系统、输入和游戏对象管理。如果 PixiJS 层开始承担过多游戏逻辑，再评估迁移或局部引入 Phaser。

Unity 暂不作为主路线。Unity WebGL 可以发布到浏览器，但会引入更重的构建、加载、内存和前后端集成成本。除非项目转向重 3D、Steam 桌面优先或大量 Unity Asset 工作流，否则当前阶段用 Web 技术栈更稳。

桌面分发预留 Tauri/Electron 路径。Tauri 支持复用 Web 前端并打包为跨平台桌面应用；Electron 提供更一致的 Chromium 运行环境。Startup Sim 应保持 Web 前端可独立运行，后续再选择包装层，而不是现在切换到 Unity 工程。

## 3. 产品支柱

### 3.1 可操作办公室

办公室不再只是背景。它是主游戏空间：

- 产品室：研发产品、修复质量、探索 PMF。
- 销售区：寻找客户、推进大客户、提升 MRR。
- 服务器区：支撑产品稳定性、AI 成本、交付能力。
- 会议室：董事会、融资、战略、重大事件。
- 招聘区：招募员工、调整团队结构、管理士气。
- 前台/市场区：品牌、媒体、活动、客户线索。

玩家应该能点击房间进入行动，而不是只在底部输入命令。

### 3.2 行动卡代替财务考试

每个复杂系统必须变成可读的行动卡：

- 研发冲刺：产品提升快，现金消耗高。
- 小步验证：产品提升慢，但能减少闭门造车风险。
- 增长投放：用户上升快，但产品差时会放大流失。
- 招聘扩张：产能提升，但固定支出上升。
- 融资谈判：现金增加，但股权和董事会压力变化。
- 控制成本：延长现金流可支撑时间，但增长放慢。

行动卡只显示取舍，不展示公式。详情可展开给高阶玩家看。

### 3.3 AI 角色是玩法，不是聊天装饰

AI 应嵌入角色和系统：

- CFO：现金流、预算、融资、破产预警。
- CTO：产品质量、技术债、研发路线。
- COO：交付、团队士气、组织压力。
- 投资人：估值、增长、风险偏好、谈判反馈。
- 客户：需求、抱怨、续费、流失原因。
- 竞品：价格战、产品升级、抢客户、融资消息。
- 媒体/市场：声誉、舆情、行业叙事。

AI 输出必须遵守规则：解释状态、生成叙事、提出建议、回应自由命令；不直接决定数值结果。

### 3.4 可复盘故事

每局游戏要能生成可记忆的故事：

- 你为什么失败或成功。
- 关键转折点是什么。
- 哪个角色提醒过你。
- 当时有哪些可选补救。
- 下局可以怎么改。

失败不是惩罚弹窗，而是一次可复盘的创业故事。

## 4. 核心循环

### 4.1 单回合循环

1. 观察办公室状态、核心矛盾和事件提示。
2. 点击房间或行动卡，选择本月经营动作。
3. 可选：输入自由 CEO 指令，AI 帮助解析成动作组合。
4. 系统通过 TurnEngine 结算数值、事件、竞品、客户和董事会反馈。
5. 以月度战报形式展示变化、原因、角色反馈和下一回合压力。

### 4.2 中期循环

1. 建立产品基础。
2. 找到可验证客户需求。
3. 在现金流压力下选择增长、融资或收缩。
4. 扩张团队和销售体系。
5. 形成产品、市场、资本或大客户路线。

### 4.3 长期循环

1. 形成公司风格：产品信仰、资本狂飙、大客户、精益创业、产业合作等。
2. 解锁更复杂系统：PMF、回款、毛利、组织、合规、上市路径。
3. 进入结局：破产、被迫出售、A 轮成功、行业独角兽、IPO、技术孤岛、创始人出局等。

## 5. AI 系统设计边界

### 5.1 AI 可做

- 自由命令解析：把“这个月先保现金，同时找两个试点客户”转换成可执行动作建议。
- 角色反馈：不同角色用不同立场评价本月结果。
- 事件叙事：把数值变化包装成可读故事。
- 复盘生成：从行动记录中提炼关键转折和下局建议。
- 轻量记忆：角色记住玩家行为模式，形成连续反馈。

### 5.2 AI 不可做

- 不直接修改现金、用户、估值、产品分等核心数值。
- 不绕过 StateGuard 和 TurnEngine。
- 不凭空生成投资方董事，除非游戏状态中已有融资或外部投资关系。
- 不把专业指标默认压给玩家。
- 不让自由文本变成无限制沙盒；所有命令必须进入可验证动作集合。

### 5.3 AI 架构建议

```text
Player Input
  -> Intent Parser / AI Command Interpreter
  -> ActionPlan
  -> StateGuard
  -> TurnEngine deterministic simulation
  -> Event + Board + Customer + Competitor facts
  -> AI Narrative Layer
  -> Frontend monthly report
```

AI 层消费事实，不替代事实。

## 6. 技术架构方向

### 6.1 当前保留

- `src/core/`：继续作为商业规则和回合结算核心。
- `src/api/app.py`：继续作为前端 API 包装层。
- `frontend/`：继续使用 React + Vite + TypeScript。
- Vercel：继续作为 Web 试玩和线上验收环境。
- `design-assets/`：继续作为 image-2 生成资产库。

### 6.2 新增方向

前端新增游戏层：

```text
frontend/src/game/
  engine/
  scenes/
  sprites/
  interactions/
  adapters/
```

建议边界：

- React 管信息结构、状态、表单、右侧面板、复盘页。
- PixiJS 管办公室画布、人物、房间热点、气泡、事件动画。
- Zustand 作为 React 与游戏画布之间的状态桥。
- API 只返回事实和状态，不返回画布指令。

### 6.3 分发预留

项目应避免绑定单一线上环境：

- Web 版：Vercel 部署，适合公开试玩和快速迭代。
- PWA 版：保留离线缓存和本地存档空间。
- 桌面版：未来用 Tauri 或 Electron 包装同一前端。
- Steam 版：桌面包装后接入本地存档、成就、离线 demo、可选在线 AI。

后续若要离线可玩，必须提供非 AI fallback：

- 固定模板事件和角色反馈。
- 本地规则结算。
- AI 仅作为增强体验，而不是启动游戏的必要条件。

## 7. 资产与美术管线

所有生成型前端视觉资源继续遵守：

- 使用 image-2。
- 进入 `design-assets/manifest.json`。
- Prompt 存入 `design-assets/image-2/prompts/`。
- 可复用导出存入 `design-assets/image-2/exports/`。
- 前端引用 `frontend/public/assets/` 下的注册导出。

资产优先级：

1. 办公室房间背景和可点击区域。
2. 员工/董事会/客户头像。
3. 行动卡插画。
4. 事件/危机/成就图标。
5. 结局复盘插画。

重要 UI 文案不应烘焙进图片，应由 React/CSS 渲染。

## 8. 路线图

### Alpha 0.2：独立游戏化核心切片

目标：玩家打开网页后，能感觉这是一个经营游戏，而不是仪表盘。

范围：

- 引入 PixiJS 游戏画布。
- 办公室房间可点击。
- 行动卡面板替代底部纯按钮。
- 单回合月度战报升级：变化、原因、事件、角色反馈、下一步压力。
- 自由命令保留为 CEO 指令输入。
- Vercel 线上 smoke 覆盖点击房间和提交一回合。

验收：

- 玩家能点击至少 4 个房间。
- 每个房间打开不同行动卡。
- 提交一回合后有明显视觉反馈。
- 董事会、竞品、客户或事件至少一个以气泡/战报方式出现。

### Alpha 0.3：AI 角色与自由命令

目标：AI 成为玩法的一部分。

范围：

- AI 命令解释器：自由命令 -> 可执行 ActionPlan 候选。
- CFO/CTO/COO 角色记忆原型。
- 客户反馈和竞品反馈进入事件流。
- AI 生成月度叙事，但数值由 TurnEngine 决定。

验收：

- 玩家输入非模板命令时，系统能解释将执行哪些动作。
- AI 反馈引用本局历史行为。
- AI 输出不会突破游戏状态约束。

### Alpha 0.4：办公室经营与团队系统

目标：办公室空间开始影响经营能力。

范围：

- 员工卡：能力、士气、岗位。
- 房间升级：产品室、销售区、服务器区、会议室。
- 固定支出和效率挂钩。
- 简化队列或产能系统。

验收：

- 招聘会改变办公室可视状态。
- 房间升级能影响行动效果或成本。
- 玩家能形成至少两种不同经营风格。

### Alpha 0.5：复盘、成就与结局演出

目标：失败和成功都变成可分享故事。

范围：

- ReviewEngine 前端化。
- ReplayEngine 前端时间线。
- AchievementEngine 前端成就页。
- 结局插画和创始人画像。

验收：

- 一局结束后进入复盘页。
- 展示关键转折、创始人画像、成就和下局建议。
- 至少 5 个结局有不同文案和视觉气质。

### Beta：可分发独立游戏准备

目标：从网页试玩走向可发行产品。

范围：

- 桌面包装方案评估：Tauri 优先，Electron 备选。
- 本地存档和导入导出。
- 离线 demo 模式。
- 性能预算、资源压缩、加载页。
- Steam 页面素材和试玩版包体准备。

验收：

- 同一套前端可 Web 运行，也可桌面包装。
- 没有 Vercel 也能启动离线 demo。
- AI 不可用时，核心经营循环仍可玩。

## 9. 当前不做

- 不切 Unity 主工程。
- 不做完整 3D 办公室。
- 不做多人联机。
- 不引入复杂上市、债务、回款、PMF 多指标系统到玩家默认界面。
- 不让 AI 直接生成或修改核心数值。
- 不为了“真实商业”牺牲新手可读性。

## 10. 下一步执行建议

下一步应启动 `Alpha 0.2`：

1. 新建 `frontend/src/game/` 游戏层。
2. 引入 PixiJS。
3. 把办公室图作为 PixiJS stage 背景。
4. 建立 4 个可点击房间热点。
5. 点击房间打开行动卡。
6. 行动卡生成自然语言命令并提交 TurnEngine。
7. 回合结果升级为月度战报。
8. 本地和 Vercel 都跑 smoke。

这一步是项目从“前端壳”变成“独立游戏核心切片”的关键。
