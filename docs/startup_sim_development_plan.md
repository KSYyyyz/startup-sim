# 创业模拟器完整开发规划

状态：当前总规划
日期：2026-05-18
负责人：Codex

## 1. 项目定位

Startup Sim 是一款以创业公司经营为主题的俯视角办公室建造与管理模拟游戏。

一句话目标：

> 玩家作为 SaaS 创始人，通过经营公司取得收入、利润、融资、市场地位和成就；办公室区域、设施、员工成长和日常管理是支撑公司发展的系统，而不是最终目标本身。

项目第一原则：

> 真实商业作为底层逻辑，游戏性作为表层体验。

玩家不应该被迫参加财务考试，也不应该主要通过 CLI 式文字指令游玩。复杂机制用于后台推演，前台主体验必须围绕公司经营发展、收益增长、目标达成、成就解锁和可复盘故事展开。办公室建设、设施升级和员工调配服务于这条主线。

## 2. 当前路线结论

后续主线：

- 表现层：`godot/StartupSimGodot/`
- 规则核心：`csharp/StartupSim.Core/`
- 完整参考实现：`src/core/`
- 内容数据层：`godot/StartupSimGodot/data/` 与 `data/`
- 资产库：`design-assets/` 与 `godot/StartupSimGodot/assets/`

已经停止的路线：

- 不再维护 Vercel/Web 前端。
- 不再新增 Unity 主线代码。
- 不再把 CLI/飞书作为最终游戏形态。

保留的路线：

- Python CLI/飞书代码作为完整规则参考和回归测试来源保留。
- C# Core 逐步迁移 Python 规则，直到可以支撑 Godot 离线完整游玩。
- Godot 成为唯一正式前端和可分发桌面端。

## 3. 产品体验目标

### 3.1 目标体验

玩家进入游戏后看到的是一个俯视角创业办公室，而不是仪表盘墙或 CLI 指令窗口。

核心体验包括：

- 经营公司取得收益：收入增长、现金流改善、市场份额扩大、融资成功、成就解锁。
- 选择公司发展方向：产品领先、销售驱动、稳健盈利、资本扩张、大客户路线等。
- 从区域划分目录选择研发区、销售区、服务器区、会议区、招聘区等部门。
- 在办公室平面中以大像素区块为单位框定部门区域。
- 在每个部门区域中摆放设施，例如办公桌、白板、服务器、会议桌、电话工位、咖啡机。
- 为设施设置升级梯度，等级越高，价格越贵，提供的效率、士气、容量或稳定性增益越高。
- 通过员工管理入口招聘员工、查看特性、安排部门、培训或调整团队；员工会根据自身状态自主工作、休息和处理需求。
- 通过董事会、客户、竞品、团队反馈理解经营压力。
- 在现金流可支撑时间、产品能力、用户增长、融资压力之间做取舍。
- 每回合结束看到清晰月报：发生了什么、为什么、下月压力是什么。
- 每局结束进入复盘：关键转折、失败原因、可改进策略、成就。

### 3.2 玩家可见语言

必须使用玩家能理解的表达。

使用：

- 现金流可支撑时间
- 本月焦点
- 经营洞察
- 董事会争议
- 竞品态势
- 客户反馈
- 回合结果

避免默认展示：

- Runway
- LTV/CAC
- Gross Margin
- ARR Growth
- PMF 复杂公式
- 上市板块法规

高级指标可以进入详情层，但不能压在主界面。

### 3.3 失败体验

失败不是惩罚弹窗，而是一段可复盘创业故事。

每个失败结局都必须回答：

- 为什么失败。
- 哪些信号提前出现过。
- 当时有哪些可选补救。
- 下局可以换哪条路线。

## 4. 目标玩家与产品形态

优先目标玩家：

- 喜欢模拟经营、策略取舍、公司成长题材的玩家。
- 能接受文字反馈，但希望有可操作空间和视觉反馈。
- 对创业、商业竞争、融资故事和空间经营有兴趣。

产品参考方向：

- 《疯狂游戏大亨2》：长期经营、办公室空间、内容库、公司成长。
- 《Big Ambitions》：商业布局、场景配置、外置内容数据。
- 《Game Dev Tycoon》：轻量循环、事件反馈、Mod 边界。
- 《STONKS-9800》：简单数据文件、名字库、本地化和扩展入口。

Startup Sim 不直接复制任何参考游戏玩法、素材或代码，只吸收工程组织、空间经营、员工管理和产品结构经验。

公开资料参考结论：

- 《Mad Games Tycoon 2》强调自建办公室、生产设施、服务器房、招聘人才和从小车库成长为大公司。
- 《Big Ambitions》强调租赁/购买建筑、装修、设施、雇员、管理层和业务基础设施。
- 《Game Dev Tycoon》强调从小办公室开始、研发技术、搬到更大办公室、招聘并训练团队。
- 《Game Dev Story》强调员工属性、培训、办公室升级和更大团队容量。

这些参考共同指向：Startup Sim 的核心不应是文字行动列表，而应是办公室空间、部门区域、设施和员工共同驱动的经营循环。

## 5. 总体架构

```text
Player
  -> Godot 俯视角办公室经营层
  -> 内容数据库
  -> 公司目标 / 区域 / 设施 / 员工管理器
  -> 经营产能与经营意图
  -> C# Core StateGuard
  -> C# Core 时间推进与经营结算
  -> 事实快照
  -> Godot 月报 / 复盘 / 成就
```

### 5.1 Godot 表现层

Godot 负责：

- 办公室场景。
- 俯视角办公室网格。
- 区域框定、编辑和撤销。
- 设施摆放、移动、出售和升级。
- 员工管理、招聘、分配和特性展示。
- 行动卡作为设施、区域和员工管理的辅助解释入口。
- HUD 与月报。
- 角色反馈、动画、音效、镜头和交互。
- 本地存档和桌面端导出。

Godot 不负责：

- 重写现金、估值、融资、竞品、客户、董事会规则。
- 绕过 C# Core 修改核心数值。
- 在 UI 层硬编码大量游戏内容。
- 把空间建设仅仅做成背景图热点。

### 5.2 C# Core 规则核心

C# Core 负责：

- 动作解析。
- 预算和现金校验。
- 回合结算。
- 产品、用户、MRR、估值、股权、声誉、团队等状态变化。
- 董事会、竞品、客户、经营洞察、结局的事实快照。
- 可重复测试的确定性规则。

### 5.3 Python 参考实现

Python 继续负责：

- 作为完整规则参考。
- 作为回归测试来源。
- 作为迁移对照。
- 在 C# Core 未完整对齐前，不删除 `src/core/`。

删除 Python 参考实现的前置条件：

- C# Core 已覆盖完整 12 个月基础局。
- C# Core 已覆盖融资、StateGuard、董事会、竞品、客户、洞察、结局和复盘。
- Godot 可以离线完成一局并展示完整复盘。
- Python 与 C# 的 golden case 对齐通过。
- CI 不再依赖 Python 规则测试。

## 6. 核心玩法循环

### 6.0 玩法层级与细分玩法

核心玩法确定后，Startup Sim 的玩法必须按三层展开：主线玩法、支撑玩法、反馈玩法。三层之间的关系是：主线给玩家目标，支撑层提供可操作杠杆，反馈层把结果讲清楚并形成复盘故事。

#### 主线玩法

主线玩法回答“玩家为什么继续玩这一局”。玩家追求的不是把办公室摆满，而是让公司持续成长并取得阶段性成果。

- 公司阶段目标：做出 MVP、获得首批付费客户、月经常收入突破关键节点、完成 A 轮融资、市场排名进入前三、进入盈利状态。
- 产品经营：研发版本、修复 Bug、提升稳定性、做差异化功能、验证客户需求、选择产品路线。
- 收益增长：获客、留存、定价、大客户、订阅收入、现金流可支撑时间、利润质量。
- 成就和结局：产品神话、现金流大师、销售机器、技术孤岛、创始人出局、被收购、IPO 等。

主线玩法的验收标准：

- 每个月都能回答“公司离目标更近还是更远”。
- 每个阶段目标都能被办公室、设施、员工和经营结果推动。
- 玩家能从月报中看到公司成长，而不是只看到若干数值变化。

#### 支撑玩法

支撑玩法是玩家最常操作的内容，但它们不能脱离公司主线单独膨胀。

- 办公室区域玩法：研发区、销售区、服务器区、会议区、休息区、招聘区等。每个区域对应一种公司能力。
- 设施玩法：办公桌、白板、服务器、电话工位、会议桌、咖啡机、休息设施等。每个设施有等级、维护费、容量、增益和副作用。
- 员工管理玩法：招聘、岗位分配、能力查看、特性判断、薪资压力、离职风险。
- 员工成长玩法：岗位经验、培训、导师带教、项目突破。成长结果反馈到产品速度、销售转化、稳定性、客户满意和组织效率。
- 员工需求玩法：疲劳、情绪、健康、厕所、休息、娱乐。需求系统只影响效率、事故和离职风险，不做成照料模拟器。

支撑玩法的验收标准：

- 每个支撑系统都必须带来一个可理解的经营取舍。
- 每个设施、区域或员工变化都必须能追溯到公司能力变化。
- 玩家不需要阅读公式，也能理解“为什么这个改动让公司变强或变危险”。

#### 反馈玩法

反馈玩法回答“刚刚发生了什么，以及为什么”。它决定游戏是否有记忆点。

- 月度战报：展示本月赚了多少、亏了多少、哪里增长、哪里出问题。
- 董事会反馈：只基于真实结算事实，不凭空产生投资人、董事或经营结论。
- 竞品态势：竞品融资、降价、产品升级、抢客户、媒体曝光。
- 经营洞察：把复杂商业指标翻译成人话，默认不展示专业公式。
- 复盘系统：解释失败或成功原因、关键转折、当时可选补救、下局改进方向。

反馈玩法的验收标准：

- 每条反馈都能追溯到结算后的事实快照。
- 失败不能只是惩罚弹窗，必须能形成可复盘故事。
- 信息默认克制，详情可以展开，避免重新变成文字仪表盘。

#### 第一版实现顺序

G1 之后的细分玩法应按以下顺序推进：

1. 办公室区域和设施摆放。
2. 员工招聘和岗位适配。
3. 员工成长和需求状态。
4. 区域、设施、员工转化为公司产能。
5. 产品、客户、收入结算。
6. 月报、竞品、董事会和复盘反馈。

第一版不要急着加入融资、上市、复杂 PMF、多指标财务或 AI 玩法。优先打磨这一条闭环：玩家划分研发区、招人、买设施、员工成长、产品变强、收入增长，并在月报里看懂原因。

### 6.1 公司经营主循环

1. 游戏时间持续推进，玩家可暂停、正常速度、二倍速或三倍速运行。
2. 玩家观察公司目标、收益、现金流可支撑时间、订单/客户、产品进展和部门瓶颈。
3. 玩家通过区域、设施和员工管理改善公司能力。
4. 员工在时间推进中自主工作、休息、娱乐、上厕所、产生情绪波动或生病。
5. C# Core 按时间片和月度节点结算产出、成本、收入、风险和成就进度。
6. Godot 展示公司经营结果、部门状态、员工反馈、董事会、竞品态势、客户反馈和经营洞察。
7. 历史事实进入复盘记录。

### 6.2 区域和设施辅助循环

1. 规划部门区域。
2. 摆放基础设施。
3. 招聘员工填充工位。
4. 观察部门产出和瓶颈。
5. 升级设施或扩区。
6. 支付更高固定支出。
7. 通过更高产出换取产品、用户、营收、声誉或融资能力。

### 6.3 员工自主模拟循环

1. 招聘候选人。
2. 查看员工能力、特长、职位适配、薪资、特性、成长潜力和负面标签。
3. 分配到合适部门和工种。
4. 员工根据工作时间、疲劳、情绪、健康和生理需求自主选择工作、休息、娱乐、上厕所或请病假。
5. 通过设施、培训和管理提升能力与产出。
6. 处理疲劳、士气、离职风险、生病、低效和关键人才瓶颈。

员工特性要求：

- 每个员工都有随机正面和负面特性。
- 特性会影响效率、情绪、学习速度、团队协作、稳定性、离职风险或特殊事件。
- 员工能力和特长决定适合的职位和工种，例如研发、销售、运营、客服、服务器维护、人事、财务等。
- 员工成长不能喧宾夺主，必须服务于公司经营收益和发展目标。

### 6.4 员工成长系统

员工成长是公司经营主线的长期杠杆，不是独立养成游戏。玩家培养员工的目的，是让公司获得更稳定的产出、更高的岗位匹配、更少的事故和更强的阶段目标完成能力。

成长来源：

- 自然经验：员工在匹配岗位持续工作，会缓慢积累对应能力经验。
- 定向培训：玩家花费时间和现金安排培训，短期降低产出，长期提高能力或解锁专长。
- 项目突破：产品发布、重大客户签约、融资成功、危机处理等事件会给相关员工成长机会。
- 导师带教：高能力员工或管理岗可以提升同部门新人学习速度，但会占用一部分资深员工产能。

成长维度：

- 专业能力：研发、销售、运营、客服、服务器维护、人事、财务等。
- 协作能力：影响团队效率、跨部门摩擦和项目稳定性。
- 抗压能力：影响危机、加班、融资压力和客户投诉下的情绪波动。
- 管理能力：影响团队容量、带教效率、离职风险和部门执行稳定性。
- 学习潜力：影响经验获取速度和培训收益。

玩家可见表达：

- 不默认展示复杂公式，只展示等级、经验趋势、岗位适配、成长潜力和近期变化。
- 员工详情页可以显示“适合岗位”“近期成长”“当前瓶颈”“建议培养方向”。
- 月报只展示与经营结果有关的成长，例如“研发组通过版本攻坚提升了交付稳定性”。

约束：

- 员工成长必须有成本：现金、时间、导师产能、疲劳或短期机会成本。
- 成长收益必须反馈到公司主线：产品能力、销售转化、客户满意、服务器稳定、组织效率、现金流压力或成就进度。
- 员工不会无限成长。每名员工有潜力上限、成长曲线和适配方向，避免所有人最终同质化。
- 负面特性不能只靠成长完全抹掉，只能通过管理、岗位调整、设施或培训降低影响。

### 6.5 中期循环

1. 验证产品方向。
2. 获得早期用户。
3. 面对现金流可支撑时间压力。
4. 在扩区、买设施、招聘、融资、节流之间取舍。
5. 形成公司路线风格。

### 6.6 长期循环

1. 路线成型：产品信仰、资本狂飙、大客户、精益创业、产业合作。
2. 逐步解锁 PMF、销售体系、回款、毛利、组织压力、合规、上市路线。
3. 进入多种结局：破产、勉强存活、A 轮成功、被收购、技术孤岛、创始人出局、独角兽、IPO。

### 6.7 CLI 旧玩法定位

CLI/飞书版本不再代表最终核心玩法。它们只保留为：

- 规则参考实现。
- 回归测试入口。
- 快速数值验证工具。

Godot 版的核心玩法必须以办公室空间建设和员工设施管理为准。

## 7. 阶段解锁设计

复杂度必须渐进解锁。

| 阶段 | 玩家关注 | 新增概念 |
| --- | --- | --- |
| 0-12 个月 | 活下去、做出产品、获得第一批收入 | 现金流、产品、客户、基础员工需求 |
| A 轮后 | 提高收入、扩大团队、稳定交付 | 部门扩张、员工成长、设施升级 |
| B 轮后 | 建立销售体系、提升利润质量 | 大客户、回款、毛利、组织效率 |
| C 轮后 | 形成行业地位和规模优势 | 董事会、战略合作、竞品并购 |
| Pre-IPO | 盈利、治理、上市选择 | 合规、审计、上市路径 |

每个阶段只引入 1-2 个新概念。

## 8. 行动系统

### 8.1 基础空间动作

第一阶段必须支持：

- 查看公司目标、收益和成就进度。
- 调节游戏速度：暂停、正常速度、二倍速、三倍速。
- 划分研发区。
- 划分销售区。
- 划分服务器区。
- 划分会议区。
- 摆放基础办公桌。
- 摆放白板或研发设施。
- 摆放电话工位或销售设施。
- 摆放服务器或云成本设施。
- 升级设施。
- 招聘员工。
- 分配员工到部门。
- 查看员工能力、特长、正负特性、疲劳、情绪、健康和需求。
- 安排培训或调整工种。

每个空间动作必须包含：

- 玩家可读名称。
- 所属目录。
- 占用区块。
- 适用阶段。
- 成本或资源消耗。
- 主要收益。
- 主要风险。
- 一句人话解释。

### 8.2 衍生经营行动

以下经营行动不再作为主界面核心按钮，而应由区域、设施和员工状态自然产生：

- 研发产品：来自研发区面积、研发设施、研发员工能力和员工状态。
- 市场营销：来自销售/市场区、营销设施、销售员工能力和员工状态。
- 招聘人才：来自招聘入口、HR 能力、公司声誉。
- 融资谈判：来自会议区、公司数据、投资人关系。
- 控制成本：来自设施维护、员工薪资、区域闲置率。
- 客户验证：来自销售区、客户成功员工、试点客户事件。

### 8.3 暂不做自由指令

近期 Godot 主线不做自由 CEO 指令、自然语言解析、AI 对话或模型接入。

保留规则：

- 玩家主要通过办公室区域、设施和员工操作推进游戏。
- CLI 自然语言解析只作为旧原型和测试入口保留。
- 后续如恢复自由指令，也必须先转换成结构化经营意图，再经过 StateGuard 和 C# Core。
- 自由指令永远不能直接改写核心状态。

### 8.4 避免一键依赖

系统不能鼓励玩家依赖“一键生成最优指令”。

建议系统的定位：

- 解释当前局势。
- 提醒风险。
- 给方向，不给唯一答案。
- 提供 2-3 个风格不同的策略选择。
- 不自动替玩家填入最优行动。

## 9. 董事会、竞品与客户

### 9.1 董事会

董事会反馈必须基于本回合执行后的状态。

董事会角色来源：

- CFO：现金流、预算、融资风险。
- CTO：产品、技术债、研发路线。
- COO：交付、团队、运营效率。
- 投资机构代表：只在融资或外部投资相关场景出现。
- 独立董事：后期治理阶段解锁。

没有融资或外部投资时，不得凭空出现投资方董事。

### 9.2 竞品

竞品要像真实市场压力，而不是装饰文本。

第一阶段竞品要影响：

- 获客成本。
- 市场份额。
- 用户增长。
- 声誉。
- 投资人信心。

竞品行为包括：

- 降价抢客户。
- 发布新功能。
- 融资扩张。
- 抢大客户。
- 媒体曝光。

### 9.3 客户

客户反馈是 PMF 的人话表达。

第一阶段只展示：

- 客户验证：弱 / 中 / 强。
- 产品市场匹配：未验证 / 初步验证 / 明确验证。

后台可以计算访谈数、留存、激活、付费意愿、试点客户，但默认不展示公式。

## 10. 当前不做 AI 玩法

近期开发先完全忽略 AI 玩法，集中完成办公室建造经营闭环。

当前不做：

- AI 自由指令。
- AI 角色对话。
- AI 事件叙事。
- AI 复盘生成。
- AI Agent。
- API 或模型接入。

保留边界：

- 角色反馈、董事会、竞品、客户和复盘先由确定性规则与模板生成。
- 所有经营事实必须来自 C# Core 结算。
- 未来如恢复 AI，也只能消费事实快照，不能修改核心数值。
