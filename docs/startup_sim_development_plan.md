# 创业模拟器完整开发规划

Status: active master plan
Date: 2026-05-18
Owner: Codex

## 1. 项目定位

Startup Sim 是一款以创业公司经营为主题的俯视角办公室建造与管理模拟游戏。

一句话目标：

> 玩家作为 SaaS 创始人，在俯视角办公室中划分部门区域、摆放和升级设施、招聘并管理员工，用可见的空间经营动作推动产品、增长、融资、客户和竞品博弈，走出不同创业命运。

项目第一原则：

> 真实商业作为底层逻辑，游戏性作为表层体验。

玩家不应该被迫参加财务考试，也不应该主要通过 CLI 式文字指令游玩。复杂机制用于后台推演，前台主体验必须是空间建设、设施升级、员工调配、经营反馈和可复盘故事。

## 2. 当前路线结论

后续主线：

- 表现层：`godot/StartupSimGodot/`
- 规则核心：`csharp/StartupSim.Core/`
- 完整参考实现：`src/core/`
- 内容数据层：`godot/StartupSimGodot/data/` 与 `data/`
- 资产库：`design-assets/` 与 `godot/StartupSimGodot/assets/`

已经停止的路线：

- 不再维护 Vercel/Web 前端。
- 不再新增 Unity 主线代码。
- 不再把 CLI/飞书作为最终游戏形态。

保留的路线：

- Python CLI/飞书代码作为完整规则参考和回归测试来源保留。
- C# Core 逐步迁移 Python 规则，直到可以支撑 Godot 离线完整游玩。
- Godot 成为唯一正式前端和可分发桌面端。

## 3. 产品体验目标

### 3.1 目标体验

玩家进入游戏后看到的是一个俯视角创业办公室，而不是仪表盘墙或 CLI 指令窗口。

核心体验包括：

- 从区域划分目录选择研发区、销售区、服务器区、会议区、招聘区等部门。
- 在办公室平面中以大像素区块为单位框定部门区域。
- 在每个部门区域中摆放设施，例如办公桌、白板、服务器、会议桌、电话工位、咖啡机。
- 为设施设置升级梯度，等级越高，价格越贵，提供的效率、士气、容量或稳定性增益越高。
- 通过员工管理入口招聘员工、查看特性、安排部门、培训或调整团队。
- 通过董事会、客户、竞品、团队反馈理解经营压力。
- 在现金流可支撑时间、产品能力、用户增长、融资压力之间做取舍。
- 每回合结束看到清晰月报：发生了什么、为什么、下月压力是什么。
- 每局结束进入复盘：关键转折、失败原因、可改进策略、成就。

### 3.2 玩家可见语言

必须使用玩家能理解的表达。

使用：

- 现金流可支撑时间
- 本月焦点
- 经营洞察
- 董事会争议
- 竞品态势
- 客户反馈
- 回合结果

避免默认展示：

- Runway
- LTV/CAC
- Gross Margin
- ARR Growth
- PMF 复杂公式
- 上市板块法规

高级指标可以进入详情层，但不能压在主界面。

### 3.3 失败体验

失败不是惩罚弹窗，而是一段可复盘创业故事。

每个失败结局都必须回答：

- 为什么失败。
- 哪些信号提前出现过。
- 当时有哪些可选补救。
- 下局可以换哪条路线。

## 4. 目标玩家与产品形态

优先目标玩家：

- 喜欢模拟经营、策略取舍、公司成长题材的玩家。
- 能接受文字反馈，但希望有可操作空间和视觉反馈。
- 对创业、商业竞争、融资故事和空间经营有兴趣。

产品参考方向：

- 《疯狂游戏大亨2》：长期经营、办公室空间、内容库、公司成长。
- 《Big Ambitions》：商业布局、场景配置、外置内容数据。
- 《Game Dev Tycoon》：轻量循环、事件反馈、Mod 边界。
- 《STONKS-9800》：简单数据文件、名字库、本地化和扩展入口。

Startup Sim 不直接复制任何参考游戏玩法、素材或代码，只吸收工程组织、空间经营、员工管理和产品结构经验。

公开资料参考结论：

- 《Mad Games Tycoon 2》强调自建办公室、生产设施、服务器房、招聘人才和从小车库成长为大公司。
- 《Big Ambitions》强调租赁/购买建筑、装修、设施、雇员、管理层和业务基础设施。
- 《Game Dev Tycoon》强调从小办公室开始、研发技术、搬到更大办公室、招聘并训练团队。
- 《Game Dev Story》强调员工属性、培训、办公室升级和更大团队容量。

这些参考共同指向：Startup Sim 的核心不应是文字行动列表，而应是办公室空间、部门区域、设施和员工共同驱动的经营循环。

## 5. 总体架构

```text
Player
  -> Godot Top-Down Office Builder
  -> Content Database
  -> Zone / Facility / Staff Managers
  -> Derived Action Intents
  -> C# Core StateGuard
  -> C# Core Turn Settlement
  -> Fact Snapshots
  -> Godot Monthly Report / Review
```

### 5.1 Godot 表现层

Godot 负责：

- 办公室场景。
- 俯视角办公室网格。
- 区域框定、编辑和撤销。
- 设施摆放、移动、出售和升级。
- 员工管理、招聘、分配和特性展示。
- 行动卡作为设施、区域和员工管理的辅助解释入口。
- HUD 与月报。
- 角色反馈、动画、音效、镜头和交互。
- 本地存档和桌面端导出。

Godot 不负责：

- 重写现金、估值、融资、竞品、客户、董事会规则。
- 绕过 C# Core 修改核心数值。
- 在 UI 层硬编码大量游戏内容。
- 把空间建设仅仅做成背景图热点。

### 5.2 C# Core 规则核心

C# Core 负责：

- 动作解析。
- 预算和现金校验。
- 回合结算。
- 产品、用户、MRR、估值、股权、声誉、团队等状态变化。
- 董事会、竞品、客户、经营洞察、结局的事实快照。
- 可重复测试的确定性规则。

### 5.3 Python 参考实现

Python 继续负责：

- 作为完整规则参考。
- 作为回归测试来源。
- 作为迁移对照。
- 在 C# Core 未完整对齐前，不删除 `src/core/`。

删除 Python 参考实现的前置条件：

- C# Core 已覆盖完整 12 个月基础局。
- C# Core 已覆盖融资、StateGuard、董事会、竞品、客户、洞察、结局和复盘。
- Godot 可以离线完成一局并展示完整复盘。
- Python 与 C# 的 golden case 对齐通过。
- CI 不再依赖 Python 规则测试。

## 6. 核心玩法循环

### 6.1 核心空间循环

1. 玩家观察俯视角办公室、现金流可支撑时间、本月焦点和部门瓶颈。
2. 玩家从区域划分目录选择部门类型，例如研发区、销售区、服务器区、会议区、招聘区。
3. 玩家在办公室平面上框定区域，区域大小以大像素区块为单位。
4. 玩家在区域内摆放设施，设施占用格子并提供部门容量或效率。
5. 玩家根据现金和需求升级设施，换取更高增益和更高固定支出。
6. 玩家招聘员工，查看特性，把员工分配到合适部门。
7. Godot 根据区域、设施、员工和当前经营压力生成本月可执行经营意图。
8. C# Core 通过 StateGuard 校验预算、现金、容量和风险。
9. C# Core 结算月度结果。
10. Godot 展示部门状态变化、员工反馈、董事会、竞品态势、客户反馈和经营洞察。
11. 历史事实进入复盘记录。

### 6.2 区域和设施循环

1. 规划部门区域。
2. 摆放基础设施。
3. 招聘员工填充工位。
4. 观察部门产出和瓶颈。
5. 升级设施或扩区。
6. 支付更高固定支出。
7. 通过更高产出换取产品、用户、营收、声誉或融资能力。

### 6.3 员工循环

1. 招聘候选人。
2. 查看员工角色、薪资、特性、成长潜力和负面标签。
3. 分配到部门。
4. 通过设施、培训和管理提升产出。
5. 处理疲劳、士气、离职风险和关键人才瓶颈。

### 6.4 中期循环

1. 验证产品方向。
2. 获得早期用户。
3. 面对现金流可支撑时间压力。
4. 在扩区、买设施、招聘、融资、节流之间取舍。
5. 形成公司路线风格。

### 6.5 长期循环

1. 路线成型：产品信仰、资本狂飙、大客户、精益创业、产业合作。
2. 逐步解锁 PMF、销售体系、回款、毛利、组织压力、合规、上市路线。
3. 进入多种结局：破产、勉强存活、A 轮成功、被收购、技术孤岛、创始人出局、独角兽、IPO。

### 6.6 CLI 旧玩法定位

CLI/飞书版本不再代表最终核心玩法。它们只保留为：

- 规则参考实现。
- 回归测试入口。
- 快速数值验证工具。

Godot 版的核心玩法必须以办公室空间建设和员工设施管理为准。

## 7. 阶段解锁设计

复杂度必须渐进解锁。

| 阶段 | 玩家关注 | 新增概念 |
| --- | --- | --- |
| 0-12 个月 | 活下去、做产品、拿 A 轮 | 现金流、产品、用户、融资 |
| A 轮后 | 找 PMF、增长、团队扩张 | 客户验证、留存、组织压力 |
| B 轮后 | 销售体系、回款、毛利 | 大客户、交付、毛利、回款 |
| C 轮后 | 资本结构、行业地位 | 董事会、战略合作、竞品并购 |
| Pre-IPO | 盈利、治理、上市选择 | 合规、审计、上市路径 |

每个阶段只引入 1-2 个新概念。

## 8. 行动系统

### 8.1 基础空间动作

第一阶段必须支持：

- 划分研发区。
- 划分销售区。
- 划分服务器区。
- 划分会议区。
- 摆放基础办公桌。
- 摆放白板或研发设施。
- 摆放电话工位或销售设施。
- 摆放服务器或云成本设施。
- 升级设施。
- 招聘员工。
- 分配员工到部门。

每个空间动作必须包含：

- 玩家可读名称。
- 所属目录。
- 占用区块。
- 适用阶段。
- 成本或资源消耗。
- 主要收益。
- 主要风险。
- 一句人话解释。

### 8.2 衍生经营行动

以下经营行动不再作为主界面核心按钮，而应由区域、设施和员工状态自然产生：

- 研发产品：来自研发区面积、研发设施、研发员工。
- 市场营销：来自销售/市场区、营销设施、相关员工。
- 招聘人才：来自招聘入口、HR 能力、公司声誉。
- 融资谈判：来自会议区、公司数据、投资人关系。
- 控制成本：来自设施维护、员工薪资、区域闲置率。
- 客户验证：来自销售区、客户成功员工、试点客户事件。

### 8.3 暂不做自由指令

近期 Godot 主线不做自由 CEO 指令、自然语言解析、AI 对话或模型接入。

保留规则：

- 玩家主要通过办公室区域、设施和员工操作推进游戏。
- CLI 自然语言解析只作为旧原型和测试入口保留。
- 后续如恢复自由指令，也必须先转换成结构化经营意图，再经过 StateGuard 和 C# Core。
- 自由指令永远不能直接改写核心状态。

### 8.4 避免一键依赖

系统不能鼓励玩家依赖“一键生成最优指令”。

建议系统的定位：

- 解释当前局势。
- 提醒风险。
- 给方向，不给唯一答案。
- 提供 2-3 个风格不同的策略选择。
- 不自动替玩家填入最优行动。

## 9. 董事会、竞品与客户

### 9.1 董事会

董事会反馈必须基于本回合执行后的状态。

董事会角色来源：

- CFO：现金流、预算、融资风险。
- CTO：产品、技术债、研发路线。
- COO：交付、团队、运营效率。
- 投资机构代表：只在融资或外部投资相关场景出现。
- 独立董事：后期治理阶段解锁。

没有融资或外部投资时，不得凭空出现投资方董事。

### 9.2 竞品

竞品要像真实市场压力，而不是装饰文本。

第一阶段竞品要影响：

- 获客成本。
- 市场份额。
- 用户增长。
- 声誉。
- 投资人信心。

竞品行为包括：

- 降价抢客户。
- 发布新功能。
- 融资扩张。
- 抢大客户。
- 媒体曝光。

### 9.3 客户

客户反馈是 PMF 的人话表达。

第一阶段只展示：

- 客户验证：弱 / 中 / 强。
- 产品市场匹配：未验证 / 初步验证 / 明确验证。

后台可以计算访谈数、留存、激活、付费意愿、试点客户，但默认不展示公式。

## 10. 当前不做 AI 玩法

近期开发先完全忽略 AI 玩法，集中完成办公室建造经营闭环。

当前不做：

- AI 自由指令。
- AI 角色对话。
- AI 事件叙事。
- AI 复盘生成。
- AI Agent。
- API 或模型接入。

保留边界：

- 角色反馈、董事会、竞品、客户和复盘先由确定性规则与模板生成。
- 所有经营事实必须来自 C# Core 结算。
- 未来如恢复 AI，也只能消费事实快照，不能修改核心数值。

## 11. Godot 开发规划

### G0：工程骨架与桥接

状态：已完成基础切片。

验收：

- Godot 4.x .NET 工程可打开。
- Godot 项目可引用 `StartupSim.Core`。
- 主场景可启动。
- `GodotTurnBridge` 可调用 C# Core。
- CI 可构建 Godot C# 项目。

### G1：本地可玩垂直切片

目标：Godot 内完成一个办公室建设到月度结算的基础切片。

验收：

- 有俯视角办公室区域。
- 可以从区域划分目录选择至少 3 种部门区域。
- 可以以大像素区块为单位框定区域。
- 可以在区域内摆放至少 3 种基础设施。
- 设施有至少 2 个升级等级。
- 有员工管理入口。
- 可以招聘至少 3 类员工并分配部门。
- 系统根据区域、设施和员工生成本月经营产出预览。
- 回合由 C# Core 结算。
- HUD 显示现金、现金流可支撑时间、MRR、用户、产品、声誉、股权、估值。
- 月报显示本月变化、原因、董事会、竞品、经营洞察。

### G2：内容数据层

目标：办公室地图、区域、设施、员工、角色、竞品、事件从数据读取。

验收：

- `ContentDatabase` 可加载 JSON 内容。
- 内容 ID 唯一性检查通过。
- Godot 区域类型、设施、升级梯度和员工特性不再硬编码。
- 缺字段、重复 ID、引用失效会在验证脚本中失败。
- README 或 docs 写明新增内容的方法。

### G3：C# Core 规则对齐

目标：C# Core 支撑 12 个月基础局。

验收：

- StateGuard 预算拦截完整。
- 融资估值和拒绝逻辑完整。
- 董事会事实快照完整。
- 竞品事实快照完整。
- 客户事实快照完整。
- 结局与复盘事实完整。
- Python golden case 与 C# golden case 对齐。

### G4：办公室经营感

目标：办公室成为真正可操作、可扩张、可优化的经营空间。

验收：

- 区域有状态：正常、风险、机会、阻塞、改善。
- 设施有等级、维护成本、容量和效率增益。
- 员工有特性、薪资、部门适配和士气。
- 状态变化来自结算事实。
- 角色气泡来自事实快照。
- 区域、设施和员工结果有轻量动画或视觉变化。
- 信息密度低于旧 Web 仪表盘。

### G5：反馈与复盘体验

目标：规则角色反馈、月报和复盘成为清晰的经营反馈层。

验收：

- 角色反馈引用结算事实。
- 月报解释空间、设施和员工导致的变化。

## 17. 协作工作流

开发默认采用双轨思路：

- 前端/表现轨：Godot 场景、交互、HUD、月报、资产接入。
- 后端/规则轨：C# Core、内容数据、规则测试、golden case。

并行工作必须遵守：

- 前端不复制规则。
- 后端不决定最终 UI 密度。
- 双方通过结构化 snapshot 和 content data 对接。
- 每轮修改后 commit + push。
- 遇到冲突时以 C# Core 规则和 Godot 数据层边界为准。
